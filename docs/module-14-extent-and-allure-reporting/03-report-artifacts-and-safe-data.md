# Report Artifacts And Safe Data

## Mental Model

Reports are artifacts. They are files created by a test run and kept after the
run completes. Artifacts are useful because they let someone debug a failure
without rerunning the test immediately.

Artifacts can also leak data if the framework is careless. Module 14 treats
safe reporting as part of framework design.

The reporting question is not only "did the report generate?" It is also "is
the report safe to share?" That matters because reports often leave the local
machine as CI artifacts, pull request evidence, or ticket attachments.

## Artifact Map

| Artifact | Path | Produced by | Purpose |
| --- | --- | --- | --- |
| Extent HTML | `target/extent-report/extent.html` | `ExtentReportManager` | standalone human-readable report |
| Allure raw results | `target/allure-results/` | Allure TestNG integration | structured JSON files and attachments |

## Code Walkthrough

Sensitive data protection is currently visible in:

[src/test/java/com/learning/tests/models/LoginScenario.java](../../src/test/java/com/learning/tests/models/LoginScenario.java)

The record still stores the real password so tests can use it:

```java
String password
```

But `toString()` returns:

```java
password=****
```

This matters because reporting tools often call `toString()` on DataProvider
parameters.

## Safe Data Flow

`LoginScenario` still stores:

```java
String password
```

because [SauceDemoDataDrivenTest.java](../../src/test/java/com/learning/tests/saucedemo/SauceDemoDataDrivenTest.java)
needs the real password to execute login. The safe-output decision is limited
to display:

```java
password=****
```

That means:

- execution can still use the real credential.
- Allure/TestNG parameter rendering sees masked output.
- listener display names still prefer `scenarioName`.
- logs and reports are less likely to leak `secret_sauce`.

## Framework Nuances

It is not enough to avoid explicit logging of passwords. Frameworks also need
to consider implicit output:

- DataProvider parameter display.
- assertion messages.
- screenshot content.
- browser URL query strings.
- report labels and step names.
- exception messages.

Module 14 checks generated artifacts for `secret_sauce` after the suite run.
That is a practical habit for reporting modules.

The check is intentionally scoped to generated artifacts, not source data. The
test data files still contain `secret_sauce` because this is a public demo AUT.
The reporting risk is whether generated logs/reports expose it.

## TestNG Default Reports vs Extent vs Allure

| Tool | Strength | Limitation |
| --- | --- | --- |
| TestNG default output | available automatically | basic and not stakeholder-friendly |
| Extent | single readable HTML file | framework owns more setup code |
| Allure | rich labels, steps, attachments, CI-friendly results | requires result generation plus report generation |

## Artifact Ownership

| Artifact | Keep In Git? | Reason |
| --- | --- | --- |
| `target/extent-report/extent.html` | no | generated by each run |
| `target/allure-results/` | no | raw generated test results |
| `target/allure-report/` | no | generated dashboard |
| `target/logs/test-execution.log` | no | generated run log |
| `target/screenshots/` | no | generated failure evidence |
| [allure.properties](../../src/test/resources/allure.properties) | yes | source configuration for generated artifacts |
| [log4j2.xml](../../src/test/resources/log4j2.xml) | yes | source configuration for logs |

[.gitignore](../../.gitignore) keeps generated report outputs out of source
control. CI can still upload them later as build artifacts.

## Common Mistakes

- Treating `target/` files as harmless because they are not committed.
- Using raw credentials in scenario names.
- Forgetting reports can be uploaded by CI later.
- Adding every possible artifact and making reports noisy.
- Assuming screenshots cannot contain secrets.
- Checking source test data for demo passwords and confusing that with
  generated artifact leakage.
- Forgetting that Allure parameters can be rendered from `toString()`.

## Interview Readiness

Strong answer:

"A reporting framework should generate useful artifacts but must avoid leaking
sensitive data. I check not only explicit logs but also implicit places such as
DataProvider parameter rendering. In this project the login scenario keeps the
real password for execution but masks it in `toString()` so report tools show
safe output."

## Verification Checklist

After a reporting run:

```bash
test -f target/extent-report/extent.html
test -d target/allure-results
mvn allure:report
test -d target/allure-report
rg -n "secret_sauce" target/extent-report target/allure-results target/logs/test-execution.log
```

Expected:

- report artifacts exist.
- the secret search returns no matches in generated reporting/log artifacts.
- source files may still contain the public demo password.
